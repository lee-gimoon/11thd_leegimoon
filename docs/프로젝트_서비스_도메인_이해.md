# 프로젝트 협업 서비스와 도메인 이해

## 1. 이 서비스는 무엇인가

이 서비스는 여러 사용자가 프로젝트를 만들고, 프로젝트 멤버끼리 작업을 생성·배정·관리하는 협업 서비스다.

Trello, Jira, Asana의 핵심 기능을 작은 규모로 구현한다고 생각하면 된다.

## 2. 실제 사용 흐름

사용자 철수와 영희가 있다고 가정한다.

1. 철수와 영희가 사용자로 등록한다.
2. 철수가 `쇼핑몰 개발` 프로젝트를 만든다.
3. 프로젝트를 만든 철수는 자동으로 `OWNER`가 된다.
4. 철수가 영희를 프로젝트 멤버로 추가한다.
5. 철수가 `로그인 API 구현` 작업을 생성한다.
6. 해당 작업의 담당자로 영희를 지정한다.
7. 영희가 작업 상태를 `TODO → IN_PROGRESS → DONE`으로 변경한다.

전체 흐름은 다음과 같다.

```text
사용자 등록
→ 프로젝트 생성
→ 멤버 초대
→ 역할 부여
→ 작업 생성
→ 담당자 지정
→ 작업 상태 관리
```

## 3. 제공하는 기능

### 3.1 사용자 기능

- 사용자 등록
- 사용자 조회

사용자는 서비스 전체에서 한 번 만들어지는 사람이다.

```text
철수
영희
민수
```

프로젝트마다 새로운 사용자를 만드는 것은 아니다.

### 3.2 프로젝트 기능

- 프로젝트 생성
- 내가 속한 프로젝트 목록 조회
- 프로젝트 상세 조회
- 프로젝트 이름과 설명 수정
- 프로젝트 삭제

프로젝트는 사용자들이 함께 작업하는 공간이다.

```text
쇼핑몰 개발
채용 관리 시스템
회사 홈페이지 개편
```

### 3.3 프로젝트 멤버 기능

- 프로젝트에 사용자 추가
- 프로젝트 멤버 목록 조회
- 멤버 역할 변경
- 프로젝트에서 멤버 제거

역할은 세 가지다.

```text
OWNER  : 프로젝트의 최종 책임자
ADMIN  : 프로젝트와 멤버를 관리하는 관리자
MEMBER : 일반 참여자
```

### 3.4 작업 기능

- 작업 생성
- 작업 목록 조회
- 작업 상세 조회
- 작업 수정
- 작업 삭제
- 담당자 지정
- 상태 관리

작업 상태는 다음과 같다.

```text
TODO
→ IN_PROGRESS
→ DONE
```

## 4. 핵심 도메인

이 서비스의 핵심 도메인은 네 개다.

```text
User
Project
ProjectMember
Task
```

관계는 다음과 같다.

```text
             ┌──────────────────┐
             │  ProjectMember   │
             │                  │
User 1 ── N  │ user             │  N ── 1 Project
             │ project          │
             │ role             │
             └──────────────────┘

Project 1 ─────────────────────────── N Task

User 1 ────────────────────────────── N Task
                                      담당자
```

조금 더 쉽게 표현하면 다음과 같다.

```text
User
 ├─ 여러 프로젝트에 참여할 수 있다.
 └─ 여러 작업의 담당자가 될 수 있다.

Project
 ├─ 여러 멤버를 가진다.
 └─ 여러 작업을 가진다.

ProjectMember
 └─ 어떤 사용자가 어떤 프로젝트에서 어떤 역할인지 기록한다.

Task
 ├─ 반드시 하나의 프로젝트에 속한다.
 └─ 담당자는 없거나 한 명이다.
```

## 5. User

`User`는 서비스에 가입한 사람 자체를 나타낸다.

```text
User
├─ id
├─ name
└─ email
```

예시는 다음과 같다.

```text
id: 1
name: 철수
email: chulsoo@example.com
```

`User` 자체에는 `OWNER`, `ADMIN`, `MEMBER` 역할이 없다. 같은 사용자라도 프로젝트마다 역할이 다를 수 있기 때문이다.

```text
철수
├─ 쇼핑몰 프로젝트에서는 OWNER
├─ 채용 시스템에서는 ADMIN
└─ 홈페이지 프로젝트에서는 MEMBER
```

따라서 프로젝트 역할을 `User`에 저장하면 안 된다.

## 6. Project

`Project`는 여러 사용자가 함께 일하는 공간이다.

```text
Project
├─ id
├─ name
└─ description
```

예시는 다음과 같다.

```text
id: 10
name: 쇼핑몰 개발
description: 온라인 쇼핑몰 신규 개발
```

`Project`에는 소유자 ID를 직접 저장하지 않는다.

```java
project.ownerId // 이런 필드는 사용하지 않는다.
```

`OWNER`도 프로젝트 멤버 역할 중 하나이고 여러 명일 수도 있으므로 `ProjectMember`에 기록한다.

## 7. ProjectMember

`ProjectMember`는 사용자와 프로젝트를 연결하는 중요한 도메인이다.

이 엔티티는 다음 질문에 답한다.

> 어떤 사용자가 어떤 프로젝트에서 어떤 역할을 가지고 있는가?

```text
ProjectMember
├─ project
├─ user
└─ role
```

예를 들면 다음과 같은 데이터가 존재할 수 있다.

| 사용자 | 프로젝트 | 역할 |
|---|---|---|
| 철수 | 쇼핑몰 개발 | OWNER |
| 영희 | 쇼핑몰 개발 | MEMBER |
| 철수 | 채용 시스템 | ADMIN |
| 영희 | 채용 시스템 | OWNER |

같은 사용자도 프로젝트에 따라 역할이 달라진다. 따라서 사용자와 프로젝트를 직접 연결하는 것만으로는 부족하고, 역할을 저장할 수 있는 `ProjectMember`가 필요하다.

```text
User ↔ ProjectMember ↔ Project
```

같은 사용자가 같은 프로젝트에 두 번 들어가는 것은 다음 데이터베이스 제약으로 차단한다.

```text
UNIQUE(project_id, user_id)
```

## 8. Task

`Task`는 프로젝트 안에서 처리해야 하는 할 일이다.

```text
Task
├─ project
├─ title
├─ description
├─ status
└─ assignee
```

예시는 다음과 같다.

```text
프로젝트: 쇼핑몰 개발
제목: 로그인 API 구현
상태: IN_PROGRESS
담당자: 영희
```

작업은 반드시 하나의 프로젝트에 속한다.

```text
쇼핑몰 프로젝트
├─ 로그인 API 구현
├─ 상품 목록 구현
└─ 결제 API 구현
```

현재 설계에서 작업 담당자는 선택 사항이다.

```text
담당자가 있는 작업
→ 영희가 로그인 API 담당

담당자가 없는 작업
→ 아직 배정되지 않은 작업
```

최종적으로 담당자를 지정할 때는 그 사용자가 해당 프로젝트의 멤버인지 검사해야 한다. 이 검사는 3단계에서 추가한다.

## 9. 전체 데이터 예시

```text
사용자
├─ 철수(id=1)
└─ 영희(id=2)

프로젝트
└─ 쇼핑몰 개발(id=10)

프로젝트 멤버
├─ 쇼핑몰 개발 + 철수 + OWNER
└─ 쇼핑몰 개발 + 영희 + MEMBER

작업
├─ 로그인 API 구현
│  ├─ 프로젝트: 쇼핑몰 개발
│  ├─ 담당자: 영희
│  └─ 상태: IN_PROGRESS
│
└─ 결제 API 구현
   ├─ 프로젝트: 쇼핑몰 개발
   ├─ 담당자: 없음
   └─ 상태: TODO
```

## 10. 프로젝트가 중심인 이유

이 서비스의 핵심 데이터 경계는 프로젝트다.

```text
프로젝트
├─ 프로젝트 정보
├─ 프로젝트 멤버
├─ 멤버 역할
└─ 프로젝트 작업
```

사용자는 서비스 전체에 존재하지만 멤버와 작업은 프로젝트를 기준으로 격리된다.

작업 URL에도 프로젝트 ID를 포함한다.

```http
GET /api/projects/10/tasks/100
```

다음과 같이 작업 ID만 사용하지 않는다.

```http
GET /api/tasks/100
```

URL만 보더라도 `10번 프로젝트에 속한 100번 작업`이라는 데이터 경계를 알 수 있게 하기 위한 설계다.

## 11. 권한 규칙

최종 서비스에서는 역할에 따라 다음과 같이 동작한다.

| 기능 | OWNER | ADMIN | MEMBER |
|---|---:|---:|---:|
| 프로젝트 조회 | 가능 | 가능 | 가능 |
| 프로젝트 수정 | 가능 | 가능 | 불가능 |
| 프로젝트 삭제 | 가능 | 불가능 | 불가능 |
| 멤버 관리 | 가능 | 가능 | 불가능 |
| 작업 생성·조회 | 가능 | 가능 | 가능 |
| 다른 사람 작업 수정 | 가능 | 가능 | 불가능 |
| 자신이 담당한 작업 수정 | 가능 | 가능 | 가능 |

프로젝트 멤버가 아닌 사용자는 프로젝트와 작업을 조회할 수도 없다.

현재 2단계에서는 데이터 구조와 기본 CRUD까지 구현했다. 다음 규칙은 3단계에서 추가한다.

- 프로젝트 역할별 권한 검사
- 프로젝트 비멤버 접근 차단
- 마지막 `OWNER` 강등·제거 방지
- 작업 담당자가 해당 프로젝트 멤버인지 검증
- 작업 수정·삭제 권한 검사
- 낙관적 락과 동시 수정 충돌 처리

## 12. 핵심 정리

> 사용자는 여러 프로젝트에 참여할 수 있고, `ProjectMember`가 프로젝트별 역할을 기록한다. 프로젝트에는 여러 작업이 있으며, 각 작업은 프로젝트 멤버 중 한 명에게 배정되거나 담당자 없이 존재할 수 있다.
