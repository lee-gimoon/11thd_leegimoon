# 작업 동시성 문제 해결 방법

## 1. 해결 방법의 핵심

수정 SQL 자체에 **현재 버전이 내가 봤던 버전과 같은 경우에만 수정한다**는 조건을 넣습니다. 버전 확인과 수정이 하나의 SQL에서 원자적으로 일어납니다.

## 2. 최초 작업 상태

처음 `tasks` 테이블의 상태가 다음과 같다고 하겠습니다.

| id | title | status | version |
| :-- | :-- | :-- | --: |
| 1 | REST API 구현 | TODO | 0 |

A와 B가 모두 이 데이터를 조회합니다.

```text
A가 본 버전: 0
B가 본 버전: 0
```

## 3. A의 수정 성공

A가 수정하면 DB에서 다음과 같은 SQL이 실행됩니다.

```sql
UPDATE tasks
SET status = 'IN_PROGRESS',
    version = 1
WHERE id = 1
  AND version = 0;
```

현재 DB 버전이 `0`이므로 A의 수정은 성공합니다.

| id | title | status | version |
| :-- | :-- | :-- | --: |
| 1 | REST API 구현 | IN_PROGRESS | 1 |

## 4. B의 수정 충돌

이후 B도 자신이 봤던 `version=0`으로 수정합니다.

```sql
UPDATE tasks
SET title = 'API 개발',
    version = 1
WHERE id = 1
  AND version = 0;
```

하지만 현재 DB 버전은 이미 `1`입니다.

```text
WHERE id = 1 AND version = 0
                            ↑ 불일치
```

따라서 수정되는 행이 0개입니다. Hibernate는 이를 보고 다른 요청이 먼저 수정했다고 판단하여 낙관적 락 예외를 발생시킵니다.

```text
A의 UPDATE 결과: 수정된 행 1개 → 성공
B의 UPDATE 결과: 수정된 행 0개 → 충돌
```

Spring에서는 B에게 `409 Conflict`를 반환합니다.

```json
{
  "code": "TASK_VERSION_CONFLICT",
  "message": "다른 사용자가 작업을 먼저 수정했습니다.",
  "status": 409
}
```

## 5. JPA `@Version`

`@Version`을 사용하면 Hibernate가 버전 조건이 포함된 UPDATE SQL을 자동으로 만들어 줍니다.

```java
@Entity
public class Task {

    @Version
    private Long version;
}
```

## 6. 정리

핵심은 다음 한 문장입니다.

> 버전을 다시 조회한 다음 수정하는 것이 아니라, `WHERE version = 기존버전` 조건을 포함한 UPDATE를 실행해서 DB가 버전 확인과 수정을 동시에 처리합니다.

별도의 `SELECT → 버전 확인 → UPDATE`로 나누면 확인과 수정 사이에 또 다른 요청이 들어올 수 있습니다. 그래서 조건부 UPDATE 한 문장으로 원자적으로 처리합니다.

## 7. 현재 프로젝트 적용 방식

현재 프로젝트에서는 다음 두 단계로 충돌을 검사합니다.

1. 작업 조회 응답과 수정 요청에 `version`을 포함하여 오래된 화면에서 보낸 요청을 검사합니다.
2. 서비스 검사 이후 실제로 두 트랜잭션이 동시에 저장되더라도 JPA `@Version`의 조건부 UPDATE가 한 요청만 성공시킵니다.

작업 수정 요청 예시는 다음과 같습니다.

```json
{
  "title": "REST API 구현",
  "description": "동시성 처리를 적용한다",
  "status": "IN_PROGRESS",
  "assigneeId": 2,
  "version": 0
}
```

수정 성공 시 `version`은 1 증가합니다. 요청 버전이 현재 DB 버전과 다르거나 JPA가 동시 UPDATE 충돌을 감지하면 서버는 `409 TASK_VERSION_CONFLICT`를 반환합니다.
